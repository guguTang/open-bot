# 多用户与管理端

> 目标：多人分权；身份用开源 IAM，业务后台自研薄封装。  
> 相关缺口见 [缺口与下一批.md](./缺口与下一批.md)；总览见 [技术方案.md](./技术方案.md)。  
> 更新日期：2026-10-02 — 管理端删除用户先清空业务数据再软删；已含用量 runs、Casdoor role 同步、跨租户 platform 控制台。

## 工程边界

| 工程 | 职责 | 本地 |
|------|------|------|
| **`deploy/compose.yaml`（profile `casdoor`）** + `deploy/casdoor/conf` | 仅 IAM（OIDC 登录、组织/用户目录）。**不**放业务管理 UI | `:8000`（DB `:5434`） |
| **`apps/web`** | 用户产品：聊天、设置。**不**引导进入管理端 | Vite `:5173` |
| **`apps/admin`** | 业务管理端：用户/Bot/岗位引导/追踪、成员、组织默认 LLM、用量、功能开关、审计日志；UI 为 **Ant Design ProComponents**（Vite + ProLayout 侧栏路由，非 Umi Max 全量脚手架） | Vite `:5174` |
| **`services/api`** | 统一 Go API：本地 JWT + org RBAC；`/v1/admin/*` 与聊天共用同一服务 | `:18080` |

明确不做：

- 把业务 Admin 塞进 Casdoor 或继续堆在 `apps/web` 的 `/admin` 路由里
- 为管理端再开第二个 Go 服务

```
浏览器(web :5173) ──┐
浏览器(admin :5174) ─┼→ Go API :18080（JWT / org RBAC）→ Python runtime
Casdoor :8000 ──────┘   （仅 OIDC 换发本地 JWT）
```

## 角色（一期）

| 角色 | 说明 |
|------|------|
| `platform_admin` | 平台级：跨租户只读/开关等（一期主要作最高角色） |
| `org_admin` | 租户管理员：成员、默认 LLM、本 org 功能开关、审计 |
| `member` | 普通成员 |

业务权限以 Go 侧 `users.role` 为准。OIDC 换发时可按 Casdoor roles/groups 同步（见下）。

## 数据

- 表 `orgs`（默认 slug=`default`）
- `users.org_id`（可空，迁移回填）、`users.role`、`users.email`、`users.casdoor_sub`
- `org_settings`（组织默认 LLM + `feature_flags_json`）
- `org_invites`（待注册邀请）
- `audit_logs`（org 级审计：actor、action、target、meta_json）

用户和 Bot 继续手写 SQL，软删除约定：

- `users` / `agents` 的查询和更新带 `deleted_at IS NULL`。要读到已删除行时，函数注释写明 `soft-delete: include deleted`（例如审计里的操作者姓名）。
- 删除只写 `deleted_at` 与 `updated_at`。管理端删用户（单条 / 批量）走 **先 `PurgeUserData` + 侧效应（运行环境/uploads/mem0/Langfuse，与 purge-data 共用），再 `SoftDeleteUser`**：业务数据已物理清空后，账号行仍软删保留供审计。`PurgeUserData` 要求 `deleted_at IS NULL`，因此必须先清后软删；清空失败则 fail closed、不软删。
- 启动时清掉已废弃的内置 Bot 是物理删除之一，注释标记 `soft-delete: hard purge`。
- 管理端「清空业务数据」`POST /v1/admin/users/{id}/purge-data` 只硬清业务数据、**保留可登录账号**：`PurgeUserData` 在事务内硬删该用户全部业务行（含已软删 Bot），**保留 `users` 账号行**（密码/角色/org/邮箱）。函数注释标记 `soft-delete: hard purge`。`internal/db` 的测试会检查新 SQL 是否守住软删除约定。

## LLM 选用优先级（聊天 / run）

发消息时若未指定 `llm_connection_id`：

1. **用户个人覆盖**：`llm_connections` 中该用户的 `is_default`，若无则取该用户最早一条连接  
2. **组织默认**：`org_settings` 中已配置的 LLM（base_url / model / api_key 任一非空即视为已配置）  
3. **无可用连接**：不注入 `llm` payload（runtime 可走 echo / 环境变量兜底）

显式 `llm_connection_id` 始终优先于以上规则。

## 角色与产品边界（重要）

| 谁 | 用什么 | 怎么得到角色 |
|----|--------|--------------|
| **终端用户（聊天）** | 只开 `apps/web` `:5173`；`POST /v1/auth/register` / `/v1/auth/login` | 新注册**永远**是 `member`；邀请默认也是 `member` |
| **运营（业务管理端）** | 只开 `apps/admin` `:5174`；`POST /v1/admin/auth/login` | `BOOTSTRAP_ADMIN_*` 引导出 `platform_admin`，或邀请/授予 `org_admin` / `platform_admin` |
| **Casdoor IAM** | `:8000` | **不是**业务管理端；只做 OIDC 身份 |

同一 `users` 表，但**管理端不是普通用户可以用的**：`member` 调管理端登录会 **403**「此账号无管理端权限」。

邀请约定：

- `member` = 终端用户（聊天）
- `org_admin` / `platform_admin` = **管理员账号**（可登 `:5174`）
- 管理端邀请表单默认角色为 `member`

## 怎么进入管理端登录

### 终端用户

- 只启动并打开用户端：`make dev-web` → **http://127.0.0.1:5173**
- **永远不要**进管理端（`:5174`）。用户端侧栏**不再**提供「管理端」入口。

### 运营

1. **准备管理员账号（二选一）**
   - **推荐（新安装）**：在 `.env` 设置：
     ```bash
     BOOTSTRAP_ADMIN_USERNAME=ops-admin
     BOOTSTRAP_ADMIN_PASSWORD=change-me
     # 可选：BOOTSTRAP_ADMIN_EMAIL=ops@example.com
     ```
     启动 API 时：若库中尚无任何 `platform_admin`，则创建（或提升已存在同名用户为）默认组织的 `platform_admin`。
   - **已有环境**：库里已有 `org_admin` / `platform_admin`（历史首用户若已是 `platform_admin` 会保留，不再对新注册自动提权）。
2. 起 API 与管理端：
   ```bash
   make dev-api
   make dev-admin
   ```
3. 浏览器**直接**打开 **http://127.0.0.1:5174**（标题「open-bot 管理端」）。
4. 用**管理员账号**走管理端登录（`POST /v1/admin/auth/login`）。`member` 会被拒绝并提示去用户端。
5. 可选 OIDC：`POST /v1/admin/auth/oidc/exchange`（或带 `X-Client: admin` / `audience=admin`）；同样校验管理员角色。

**Casdoor `:8000` 仍是 IAM，不是业务管理端。** 不要用 Casdoor 自带的 `built-in/admin` / `123` 登 open-bot 管理端。

### 新安装 vs 已有库

| 场景 | 行为 |
|------|------|
| 新注册 `/v1/auth/register` | 一律 `member` |
| migrate 回填 | 只补 `org_id` / 空 role→`member`；**不再**把「第一个用户」提成 `platform_admin` |
| 已有 `platform_admin` 行 | **保留不动** |
| `BOOTSTRAP_ADMIN_*` | 仅当库中还没有任何 `platform_admin` 时生效 |

## 登录流

1. **用户端（聊天）**：`POST /v1/auth/login` / `register`；OIDC → `POST /v1/auth/oidc/exchange`
2. **管理端（运营）**：`POST /v1/admin/auth/login`；OIDC → `POST /v1/admin/auth/oidc/exchange`（非管理员 403）

## 管理端 UI（`apps/admin`）

- 构建：仍用 **Vite**（`make dev-admin` → `:5174`），**不**引入 Umi Max / Ant Design Pro 完整 monorepo。
- UI：`antd` + `@ant-design/pro-components`（ProLayout 侧栏、PageContainer、ProTable、ProForm）+ `react-router-dom`；`ConfigProvider` 使用 `zhCN`。
- 路由：登录页；登录后侧栏 — 用户管理 `/users`、Bot 管理 `/bots`、岗位引导 `/onboarding`、调用追踪 `/traces`、成员与角色 `/members`、默认模型 `/llm`、决策模型 `/decision`（Jev / Laya / Unsloth，默认关闭）、用量 `/usage`、组织（平台）`/orgs`、功能开关 `/flags`、审计日志 `/audit`。
- API 客户端仍为 `apps/admin/src/api.ts`（`/v1/admin/*`）；与用户端 `apps/web` 入口分离。

## 用户 / Bot / Trace API（节选）

| 方法 | 路径 | 说明 |
|------|------|------|
| GET/POST | `/v1/admin/users` | 列出 / 创建本组织用户（排除 `__a2a__`） |
| PATCH/DELETE | `/v1/admin/users/{id}` | 更新邮箱/角色/密码；**删除 = 先硬清业务数据（同 purge-data），再软删账号**（禁删自己、唯一 `platform_admin`、系统用户）。清空失败则不软删。审计 `user.delete` 带 `purged:true` / `side_effects` |
| POST | `/v1/admin/users/batch-delete` | 批量删除（每人先 purge 再软删），body：`{"ids":["..."]}`。规则与单条相同；会删光平台管理员的那些账号会被跳过；单人失败记入 `failed`，不影响其他人 |
| POST | `/v1/admin/users/{id}/purge-data` | **硬清业务数据、保留可登录账号**。body 必须 `{"confirm":"purge-data"}`。删除对话/消息、Bot、记忆与 mem0（尽力）、Langfuse traces/scores/sessions（尽力：删前收集 conversation_id 作 sessionId；按 `userId` + `metadata.user_id` + `sessionId` 列 observations 后 `DELETE /api/public/traces`（级联 observations/scores）；再按 session 清 `GET /api/public/v3/scores` 残留 session-level scores；Users/Sessions 聚合随 traces 消失；异步生效，`side_effects.langfuse` 回报计数或错误；group Auto-pick `/v1/decision/decide` 现带 user_id/conversation_id 以便匹配）、harness journal、bot_lessons、user_tool_allowlist、memory_recalls、routines、设备、密钥、MCP、usage_runs、频道/channel_members、agent_messages、运行环境主机目录与附件上传等；**不删** `users` 行、org_settings（含 decision_model 配置）、audit_logs。历史无 user/session 属性的 decision 孤立 traces 无法按用户清掉。同 org 的 `org_admin+` |
| GET/POST | `/v1/admin/bots` | 组织内助手列表 / 为组织成员创建（不含已软删除） |
| PATCH/DELETE | `/v1/admin/bots/{id}` | 更新 / 软删除非内置 Bot（校验所有者在本 org） |
| GET | `/v1/admin/traces` · `/traces/{id}` · `/traces/status` | 代理 Langfuse v4 `GET /api/public/v2/observations`（`isRootObservation`）；未配置返回 `{enabled:false}` |
| GET | `/v1/admin/memory-recalls` · `/memory-recalls/{id}` | 本轮记忆召回（runtime `meta.memory_recall` 由 Go 落库；可按 conversation / run_id / langfuse_trace_id / user / 时间过滤） |

组织范围：`org_admin` 按本 org；`platform_admin` 默认同本账号 org，可切换跨租户查看（见上）。

## 管理菜单（MVP）

| 做 | 不做 |
|----|------|
| 用户管理 CRUD（含邀请；删除=清空数据+软删；清空业务数据保留账号）`/users` | 完整计费 |
| Bot 管理（组织内助手）`/bots` | 连接器市场 |
| 调用追踪（Langfuse 代理）`/traces`（详情含「本轮召回」） | 自建全量可观测栈 |
| 记忆与压缩 `/memory`（「本轮召回」作库存/检索） | 依赖 Langfuse 才能看召回 |
| 成员邀请与角色 `/members` | |
| 跨租户组织 `/orgs`（platform_admin） | |
| 租户默认 LLM（注入成员 run） | |
| 决策模型适配层（Jev / Laya / Unsloth，默认关闭；群 Auto 选人 decision 模式经 `/v1/decision/decide`） | 把决策结果接进工具护栏或 A2A 路由 |

| 审计日志只读 | |

## Casdoor role 同步

OIDC `userinfo` 中的 `roles` / `groups`（字符串或 Casdoor `{name}` 对象）在换发本地 JWT 时映射到 `users.role`：

| 环境变量 | 说明 |
|----------|------|
| `CASDOOR_ROLE_MAP` | 显式映射，如 `admin=platform_admin,org-admin=org_admin,*=member` |
| `CASDOOR_ROLE_PLATFORM_ADMIN` | 默认 `platform_admin,admin`（逗号列表） |
| `CASDOOR_ROLE_ORG_ADMIN` | 默认 `org_admin,org-admin` |

规则：

- 新用户：有匹配则用映射角色，否则 `member`
- 已有用户：仅在匹配到映射时更新；审计 `auth.oidc_role_sync`
- **禁止**把库里最后一个 `platform_admin` 降级（审计 `auth.oidc_role_sync_blocked`）

## 本轮记忆召回

表 `memory_recalls`：每次 runtime 跑完召回后，Go 从 SSE `meta.memory_recall` 落库（含 `conversation_id` / `run_id` / `langfuse_trace_id`；并在转发给客户端前剥掉明细，只保留 `memory_recalled` / `mem0_recalled` 计数，不撑大聊天 SSE）。也可用 `POST /internal/memory-recalls`（`X-Internal-Token`）补记。

管理端「调用追踪」详情按 Langfuse trace id（或会话就近）展示本轮注入片段；「记忆与压缩 → 本轮召回」仍按用户 / 会话 / Bot / 时间做库存检索（显式 MemoryStore vs Mem0），不依赖 Langfuse。

## 用量（按 runs）

表 `usage_runs`：聊天 / A2A / defer_work / run_once 完成时记一条。token 字段在 runtime `done.usage` 有值时写入（多数流式网关可能为 0）。

`GET /v1/admin/usage?days=30`（`org_admin+`）返回计数 + `by_day` / `by_user` / `by_bot`。`platform_admin` 可用 `X-Admin-Org-Id` 或 `?org_id=` 切换查看作用域。管理端「用量」页展示。

## 跨租户 platform 控制台

仅 `platform_admin`：

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/v1/admin/platform/orgs` | 组织列表 + 汇总用量 |
| POST | `/v1/admin/platform/orgs` | 创建组织 `{slug,name}` |
| GET | `/v1/admin/platform/orgs/{id}/usage` | 指定组织细粒度用量 |
| GET | `/v1/admin/me/scope` | 当前 home/scope org |

管理端侧栏「组织（平台）」：列表、新建、设置本地作用域（影响用量页）。`org_admin` 仍只能看本组织。

组织范围说明：`org_admin` 始终本 org；`platform_admin` 默认同本账号 `org_id`，可通过 header/query 或管理端作用域切换跨租户只读查看。

## 明确不建议

- 双用户表长期并存（Casdoor 与本地 users 各一套、互不同步）——当前为 **Casdoor 身份 → 本地 users 一行**（`casdoor_sub`）。
- Fork 全栈中后台脚手架替换现有 API 面。
- 在 Casdoor 内做业务后台，或把 admin 继续嵌进 `apps/web`。
