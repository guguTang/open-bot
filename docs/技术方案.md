> 目标：体验接近 Grok Bot 的多端 AI 助手（Web / 桌面 / 移动），含多助手协作、技能、记忆、上下文压缩。
> 路径：`/Users/tangxin/Workprojects/open-bot`
> 前端锁定：React+TS + Tauri 2 + Capacitor；模型：OpenAI 兼容。
> **后端已拍板：Go（产品 API / Agent 总线）+ Python（Agent 运行时：LangGraph durable harness + Skills + Memory + Compaction + MCP）。**
> Agent 回合默认走 LangGraph（`RUNTIME_DURABLE=1`）：Postgres checkpointer、mid-turn resume、`interrupt` 人机批准、steer/follow-up；`run_tool_loop` 仅作 `RUNTIME_DURABLE=0` 回退。一次用户消息的真实路径见第 11 节。

## 2. 先拆两层，再谈语言

后端不要先选「全用 XX 语言」，先固定边界：

| 层 | 职责 | 压力类型 | 语言更在乎什么 |
|----|------|----------|----------------|
| **A. 产品 API / 网关** | 鉴权、会话 CRUD、SSE/WS 扇出、附件、助手目录、**Agent 总线**、推送钩子 | 高并发连接、稳定转发 | 并发、运维、类型清晰 |
| **B. Agent 运行时** | LLM 流式、工具/MCP、技能加载、记忆读写、上下文压缩、编排 | 模型 IO、生态库、实验迭代 | AI 生态、框架成熟度 |

两层用 **HTTP/SSE 或 gRPC + 任务队列（Redis/NATS）** 连接；契约用 **OpenAPI**（或 protobuf）固定，前端只打 A 层。

## 3. 语言组合怎么选

### 3.1 三种可行组合

| 方案 | 产品 API (A) | Agent 运行时 (B) | 适合 | 代价 |
|------|--------------|------------------|------|------|
| **① 推荐：Go + Python** | **Go**（Gin/Fiber/Echo 或 chi） | **Python**（LangGraph / 自研薄循环 + Mem0） | 你已有 Go/Python 项目经验；总线与 SSE 用 Go 稳，AI 用 Python 顺 | 两套运行时，要维护 API 契约 |
| ② 全 TypeScript | Fastify | Mastra | 前后端类型可共享；一人全栈最快 | AI 生态不如 Python 厚；和你主技术栈不完全重合 |
| ③ 全 Python | FastAPI | LangGraph / 同进程 | MVP 最快、部署简单 | 长连接扇出、多助手总线到后期更吃调优；和多端壳仍要分仓 |

不推荐一期：**Go 写完整 agent 循环**（MCP/记忆/压缩库少，重复造轮子多）、**Java/C# 上马**（无特殊编制需求时过重）。

### 3.2 为什么「Go + Python」通常更合适（对本项目）

1. **Grok Bot 类产品的脏活在网关**：多端 SSE、助手间 priority 投递、频道 fan-out、鉴权刷新——Go 擅长。
2. **技能 / 记忆 / 压缩 / MCP 的成熟开源在 Python 侧更密**：LangGraph、Mem0、各类压缩与评测工具链。
3. **TypeScript 留给前端就够**：和 Tauri/Capacitor 同语言；后端再强行全 TS 不是必须。
4. **结合方式清晰**：Go 接到「用户发消息」后，向 Python runtime 开一轮 run（流式 chunk 回传），Go 再写库、推 WS、触发总线。

### 3.3 结合方式（推荐拓扑）

```
Client (React)
    │  HTTPS / SSE / WS
    ▼
┌───────────────────────────┐
│  api-go                   │  唯一对外入口
│  · Auth / Agents / Chat   │
│  · Agent Bus / Channels   │
│  · 落库、扇出、限流        │
└───────────┬───────────────┘
            │ 内部：gRPC 或 HTTP+SSE
            │ 异步：Redis Stream / NATS（压缩、记忆抽取）
            ▼
┌───────────────────────────┐
│  agent-runtime-py         │  可水平扩多个 worker
│  · LangGraph（或薄循环）   │
│  · Skills loader          │
│  · Memory（LangGraph Store / Mem0）
│  · Compaction middleware  │
│  · MCP Client             │
└───────────────────────────┘
```

调用时序（一轮用户消息）：

1. Go 鉴权 → 写入 user message → 打开对客户端的 SSE
2. Go 调用 Python `RunAgent(conversation_id, message)`（流式）
3. Python：组装人设 + recall 记忆 + 技能目录 → 调模型 → 工具/MCP → 必要时 compact → 流式吐 token/事件
4. Go：转发 chunk；持久化 assistant message；若有 `SendToAgent` 类工具结果，走内部总线

技能 / 记忆 / 压缩仍按前文：Agent Skills 格式、分层记忆、阈值摘要；只是实现落在 **Python runtime**，由 Go 做门面。
> 上面 4 步是选型草图。现行实现见第 11 节：Go 落库并代理 SSE；Python 默认 LangGraph durable harness（`RUNTIME_DURABLE=1`），可回退手写 `run_tool_loop`。

## 10. 结论

- **后端不一定要用 TS。** TS 更适合前端；后端按层选语言更合适。
- **更合适的结合**：`Go` 做产品 API 与多助手总线，`Python` 做 Agent 运行时（技能 / 记忆 / 压缩 / MCP）。
- 想一个人先跑通：可用 **全 Python（方案 ③）** 做 Phase 0–1，接口形状按拆分设计，Phase 2 再把网关换成 Go。
- 想全员 TS：用 **Fastify + Mastra（方案 ②）**，能力对等，生态换口味。

**已拍板方案 ①。** 仓库按 Go API + Python runtime 初始化骨架。

## 11. 一轮用户消息（现行代码）

只覆盖一次交互发送：`POST /v1/conversations/{id}/messages`（不含 `persist_only`）直到助手消息落库，或这一轮改为后台。例行任务、入站 Hook 不在本节。数字来自代码常量；写了环境变量的是默认值。

### 11.1 从客户端到 Go

- Web：`apps/web/src/api.ts` 的 `sendMessageStream` 向该接口发 JSON，`Accept: text/event-stream`。桌面复用同一 Web 客户端。
- Go：`handleSendMessage`（`services/api/internal/httpserver/server.go`）。
  1. `AddMessage(role=user)` 先落库。`persist_only` 直接 JSON 返回，不跑助手。
  2. 该会话第一条 user 消息时 `autoTitleFromContent` 改标题。
  3. `resolveSendTargets`：没有频道时只有会话上的助手；群聊没有 `@everyone` 时只留第一个目标；`@everyone` 才按名单顺序各跑一轮。
  4. `tryShortcutTurn` **仅当**已有开放的 `conversation_task`。`classifySend`（`deferral.go`）不看「这句话像不像做完了」：不超过 16 个字且含「别做了 / 不用了 / 取消 / 停下 / 停止 / 停」→ 取消任务并写入「已停下。」；否则把原文入队，写入「还在做，做好会发在这里。」。两条路都不进 runtime。
  5. 否则 `activeRuns.register`：同一会话若有上一条 run，先取消并短暂等待，以便半截回复落库。Run 使用脱离 HTTP 的 context。客户端断开不取消；`POST .../cancel` 或下一次 `register` 才取消。进行中可 `GET .../events` 重接 SSE。
  6. 对每个目标：`ListMessages` → `historyForRuntime`（从最后一条 `summary` 起，保留 user / assistant / summary / system；`host_confirm` 改写成系统注记，避免模型编造允许或拒绝）。`ListEnabledSkillNamesForAgent` 只传技能**名**。附带生效的 LLM、决策设置、`client` 环境、用户时区。`proxyRuntimeRun` 调 Python `POST /v1/runs`。

### 11.2 上下文怎么拼（`run_events`）

`services/agent-runtime/app/main.py` 的 `run_events`：

1. `normalize_messages`：空正文丢掉；assistant / summary 先剥思考标签。
2. 记忆：`MemoryStore.recall_buckets`；Mem0 开启时再按 scope 检索。片段进入系统提示，并在 `meta.memory_recall` 里交 Go 记下这次召回。
3. 技能：`SkillRegistry.catalog_for_prompt` 只生成 `- 名称: 描述`。`enabled_skills is None` 表示不过滤；空列表表示当前没有启用项。全文要等模型调用 `load_skill`。
4. 工具名单：`tools_enabled` 为真时列出 `TOOL_DEFS`，再加该用户已启用 MCP 的 `mcp__*`。**没有** `host_file_query` 这个工具。本机通用命令是 `host_shell`（不限于查文件）。查文件、本机命令、SSH 的做法在技能 `host-file-query`、`host-shell`、`host-ssh`；`host-file-query` 只教如何用 `host_shell`。`load_skill` 返回正文和文件列表，不执行 `scripts/`。
5. `build_system_prompt`：`SYSTEM_PERSONA_BASE`（自主做到完成；失败换法再试、不编造工具输出；空结果先改查询；算术/时间/文件内容用工具；改代码先重读、不连打相同补丁；目录有匹配技能时动手前**必须** `load_skill(name)`（禁止未加载就调工具/本机命令），无匹配则不必 load、不是每条回复都 load；记忆只存跨会话事实；对用户中文短、只讲结果，不点内部工具名；`denied` 不得说成已执行）+ Go 传来的人设（拼在前面）+ `client_env.format_environment_block` + `format_tools_routing_block`（做法不在常驻提示里；匹配时必须 `load_skill` 再动手）+ 技能目录 + 记忆。人设、环境、路由、目录、记忆合成**一条** system。
6. **进模型前压缩**（`compact.compact_messages`，只压 user / assistant / summary）：
   - 触发（`needs_compact`）：估计 token 超过预算，或条数 > `COMPACT_MAX_MESSAGES`（默认 20），或字符 > `COMPACT_MAX_CHARS`（默认 6000）。
   - 预算 = `int(窗口 × COMPACT_BUDGET_RATIO) − COMPACT_RESERVE_OUTPUT_TOKENS`。默认窗口 32768（否则按模型名猜测，或用连接上的 `context_window`），比例 0.75，预留输出 2048。窗口夹在 4096 与 1_000_000 之间。
   - 近文大约保留预算的 1/3；不够则用 `COMPACT_KEEP_RECENT`（默认 8，且在 2 与 max_messages−2 之间）。
   - 有 API key 时用模型写中文摘要，截到 1200 字，前缀 `[对话摘要]`；失败或无 key 用 `fake_summary`。已有 summary 且其后对话没超预算则复用，不再重写。
   - `summary_new` 时 Go 以 `role=summary` 落在本条 user 消息时间戳之前 1ms，下次 `historyForRuntime` 从这里截断。

没有可用 API key 时走 `echo_events`，不进入工具循环。

### 11.3 编排：LangGraph harness（默认）与 `run_tool_loop`（回退）

默认 `RUNTIME_DURABLE=1`：`openai_path` 绑定 tool_handler 后进入 `app/harness`（prepare → llm ↔ tools → compact → finish），Postgres（或 `RUNTIME_CHECKPOINT=memory`）checkpointer；`request_id` 幂等；危险工具可 `interrupt` 批准；Go `POST .../steer` / `.../approve` 续跑。节点边界先写 **run journal**（`harness_entries` / `harness_docs` / `harness_threads`），投影成功后再对外 SSE（commit-before-show）。Langfuse 根 trace 仍包整轮，`langfuse_trace_id` 进 state 与 `memory_recall` meta；resume 跳过 Mem0 重召回。进程启动有 **resume worker** 扫描未终态 thread 自动续跑（`waiting_approval` 只发 presence，不自动跑）。

`RUNTIME_DURABLE=0` 时回退（**deprecated**）：`openai_path` 先发 `status`（正在思考），再跑 `llm.run_tool_loop`。循环里的补全是 `stream: false`。交互发送不传 `max_tool_rounds`，因此是 `DEFAULT_TOOL_ROUNDS` = **12**。显式传入时小于 1 当成 1，大于 `MAX_TOOL_ROUNDS` = **24** 则夹到 24。CI 与本地默认应按 durable 路径验证。

每一轮模型选择下一步：

- 有 `tool_calls`（正文里的 XML / Hermes 伪调用也会被解析出来）就执行 `tool_handler`，经 `guide_tool_result` 和 `truncate_tool_result_for_context` 后以 `role=tool` 追加，然后继续。工具函数抛错会变成 `ok: false` 的观察，不把整轮打崩（取消除外）。
- 没有工具调用时，若历史里已经有 `sandbox:` 产物、且本轮没用过 `sandbox_write` / `sandbox_shell`，注入一次 `CONTINUE_WORK` 再跑。若用户话像删除或列目录、却还没调用对应的 host 工具，注入一次 `CONTINUE_HOST_DELETE` 或 `CONTINUE_HOST_LIST`。这些句子只回到模型，不展示给用户。
- 本机工具的观察算失败、而模型不再调用工具：最多催促 `TOOL_FAIL_NUDGE_CAP` = **2** 次，让它换一条命令。支持 `tool_choice` 的上游对 host 工具发 `tool_choice=required`；否则追加 `TOOL_FAIL_NUDGE`。**这里不重新执行 shell。** `denied: true`，以及错误文案属于「用户拒绝 / 不允许 / 没开着 / 需要文件路径 / 端口无效」等（`_NO_RETRY_HINT`），不算可重试失败。`guide_tool_result` 只给失败的 `host_shell`（或其它 host 工具的超时）附上换命令的观察注记。
- 其余情况视为干净结束，退出循环。

本机命令的放行不在提示词里。`host_*` → `machines.exec_host` → Go `POST /internal/machines/exec`（`handleInternalHostExec`）→ `classifyHostExecReview`（`host_exec_review.go`）：

| 档 | 行为 |
|----|------|
| 硬拒绝 | `denied: true`，无确认卡（如管道进 shell、格式化磁盘） |
| 机器 `exec_policy=deny` | `denied: true`，文案为这台电脑不允许执行 |
| 确认 | 对话里等用户。`hostConfirmTimeout` = **90s**。拒绝则 `denied: true`，`error` 为「用户拒绝了这次操作」 |
| 自动 | 只读，或 `host_shell` 未命中写入/危险模式。没有正向命令白名单 |


机器策略叠在上面：`exec_policy=allow` 且 Auto-review 开时，内置确认档降为自动执行（硬拒绝仍拒绝；用户规则写了「先询问」仍确认）。`exec_policy=ask` 关掉 Auto-review，除硬拒绝外都要确认。用户自然语言规则不能推翻硬拒绝。

真正执行在已连接桌面的 WebSocket。`host_shell`：桌面 `HOST_SHELL_TIMEOUT_SECS` = **120** 秒结束进程组；stdout 与 stderr 合并，超过 **4000** 字截断并加 `…`。Go 等待 `hostExecTimeout` = **150s**（高于 120，让桌面自己返回超时）。runtime 的 HTTP 超时 `HOST_EXEC_TIMEOUT_SEC` = **180**。命令最长 2000 字。

上下文溢出：`_complete` 认出 context length 一类错误后调用 `compact_messages` 再试，最多 `_CONTEXT_OVERFLOW_RETRIES` = **2** 次，**不占**工具轮次。这一次**没有**传入 `chat_fn`，模型摘要会失败并落到 `fake_summary`（和进循环前那次不同）。压完仍不比原来短，则抛出原错误。

工具结果进上下文前：长于 `_TOOL_CONTEXT_LIMIT` = **12000** 字时保留头 **7000**、尾 **3500**，中间写明截掉多少字。

循环没干净结束、已经用过工具、且还没调用过 `defer_work` 时：若本轮仍未完成，或用过 `host_*` / `sandbox_*` / `load_skill`，或没有可展示正文，代码自己调用 `defer_work`，目标是最后一条真实用户话。入队成功则本轮可见回复固定为「还在做，做好会发在这里。」入队失败不替换这句话。干净结束不会自动推迟。

仍没有正文、且不是「只剩思考标签」时，再做**一次**不带工具的补全。若只剩思考标签或正文仍空、但已经跑过工具，用 `tool_result_fallback`：超时有固定中文；其它失败是短中文加上命令，不把失败输出当成成功；成功结果引用截到 `_TOOL_QUOTE_LIMIT` = **4000**。没跑工具又只剩思考时返回占位 `REASONING_ONLY`（不可见字符）。调用方把它清成空，**不再**开第二次流式补全，也不把占位符落库。

`<think>`、`<thinking>`、`<redacted_thinking>` 在 runtime（`strip_think_tags`）和 Go 落库前（`stripThinkTags`）都会去掉。`SYSTEM_PERSONA_BASE` 要求回复用中文、短、只讲结果，不点名内部工具。

### 11.4 存回复、推回界面

- 工具循环的最终正文**不是**模型的 token 流。`openai_path` 把整段按 **24** 字切成 `token` SSE（每段间隔 0.002 秒）。循环进行中实时推 `status`（思考、工具的中文状态、压缩、按错误改命令）。
- 只有循环返回的正文为空、且不是 `REASONING_ONLY` 时，才走 `stream_chat_tokens`（无工具的真流式），然后再切成 24 字事件。
- Python 的内层 `done` 带用量。Go `proxyRuntimeRun` 吞掉它，把 token 拼回助手正文，再 `stripThinkTags`，`saveAssistant` → `AddMessageWithAgent`，并发 `message_saved` 与 chat hub。取消且正文为空则存「（已停止）」。随后 `RecordUsageRun`。全部目标结束后外层再发一次 `done`。
- 有新 summary 时一并落库。Mem0 自动抽取和 Dream 整理在 runtime 里异步触发，不挡住这条 SSE。

### 11.5 与 pi-durable 语义对照

用户可见 transcript 仍由 **Go `messages`** 持有；run 权威在 harness journal。不引入 `@earendil-works/pi-durable` / Chord。

| pi-durable | open-bot harness |
|---|---|
| Commit 后才可见 | 节点边界写 `harness_entries`，投影后再 SSE |
| Inbox `whenBusy` | `follow_up` / `steer` / `reject`；busy 发送走 steer API |
| 进程级 `resume()` | startup + 周期 `resume_worker` 扫 `running\|interrupted` |
| Tool intent 先 commit | `tool_intent` entry；崩溃按 `replay_results` 续 |
| Compaction entry | `kind=compaction` + overflow 同 thread 重试一次 |
| Live / watch | `docs.live` 节流；细事件 `message_*` / `tool_execution_*` |
| Subagent / child | child thread + `owner_thread_id`；`defer_work` → background |
| Reset / handoff | `reset` entry；`reset_seq` 裁剪模型上下文 |
| Usage doc | `docs.usage` 累计 |
| Extensions | 进程内 `harness/registry`（tools/sections/hooks） |
| UI 批准 | `waiting_approval` → Web 批准/拒绝 → `/approve` |

**运维 / TTL**：LangGraph checkpoint 与 `harness_*` 建议按会话活跃度保留（例如 7–30 天）；可用 cron 删除 `harness_threads.updated_at` 早于阈值且 `status IN ('done','aborted','failed')` 的 thread 及其 entries/docs。checkpoint 表由 LangGraph Postgres saver 管理，清理时按 `thread_id` 对齐。`RUNTIME_JOURNAL=0` 可关掉 journal HTTP（仅测本地 graph）。

### 11.6 这一轮明确不做

- 不引入 pi-durable / 把用户可见 transcript 迁出 Go。
- 不把 `host_file_query` 注册成工具；不在代码里自动重跑同一条 host 命令。
- 用户拒绝、策略拒绝、硬拒绝都不会进入失败催促。
- 技能正文不进常驻 system prompt，只有名称和描述。
- 不做 pi-env SSH daemon / 完整 npm extension 市场。



### 11.7 对话线程（Slack / Grok 风格）

- Schema：`messages.reply_to_id`、`messages.thread_root_id`（迁移见 `db.go`）；索引 `idx_messages_reply_to`、`idx_messages_thread_root`。
- Go：`handleSendMessage` 校验父消息 → `ResolveThreadRoot` → `AddMessageWithOpts`；SSE `user_saved`；`resolveSendTargets(..., replyParent)` 在群聊无 `@` 时默认父助手；`historyForRuntime` 只看主时间线，`historyForThreadRuntime` = 可选主线 summary + 线程；`formatReplyContextPrefix` 注入 runtime 的 user content（不落库前缀）。
- Runtime：`RunRequest.reply_to_id` / `thread_root_id` / `reply_context`；召回与 Mem0 写入带线程上下文（`thread_context.py`）。
- Web：主时间线过滤 `thread_root_id` 空；线程面板；作曲回复条；`local-user-*` ← `user_saved`。
